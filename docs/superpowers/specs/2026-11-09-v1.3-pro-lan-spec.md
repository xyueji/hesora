## 1. 目标与非目标

### 1.1 目标

1. **LAN 实时协同**：一台机器作为"主机"（同时兼任收银/管理 UI），同门店 1~2 台额外 Windows 机器作为"局域网客户端"通过 HTTP+WS 访问主机的业务服务层。默认授权 3 台设备（1 主机 + 2 客户端）。
2. **可靠加密备份**：在现有每日备份基础上，提供 INVBAK v1 加密容器格式（Argon2id + AES-256-GCM），备份文件落盘到任意目录（v1.4 起上传云盘，见 `docs/alist-provider-research.md`）。
3. **统一代码库双路径**：本机路径 renderer→IPC→service 与 LAN 路径 HTTP→主机认证→service 并存，业务逻辑只在 `src/main/services/` 一份（遵守 `AGENTS.md` §3.3/§3.4 红线）。
4. **零开销基础版**：license 无 `lan_collaboration` feature 时，主机服务完全不启动（不监听端口、不建 WS、不建表外迁移之外的运行时对象），行为与 v1.2 完全一致。

### 1.2 非目标（明确不做）

- **离线客户端草稿队列**：主机不可达时客户端只读（可查本地缓存的主档/库存用于浏览），不承诺"离线开单成功"。
- **change_log / server_seq 游标增量同步**：WS 只发通知，客户端全量刷新当前页（D2）。
- **多主机**：一个门店只有一个主机实例。
- **SMB / 共享目录直写 SQLite**：绝对禁止（重申，见 §8.3）。
- **云盘直写业务数据 / 实时同步**：云盘只承担加密备份载体（v1.4），不承担事务协调。
- **跨地域写入**、**自建公网服务器**、**双机接力**（v1.4 边界，见 §7.5）。
- **移动端 / Web 客户端**。
- **主机与客户端不同版本协议协商**：v1.3 要求主机与客户端同版本安装包（同 commit 构建），不做 api_version 协商（TBD：v1.4 起评估 `protocol_version` 字段）。

### 2.2 两条请求路径（同一代码库双路径并存）

**路径 A（本机，现有路径，零改动）**：

```text
renderer 任意组件 → window.api.invoke(channel, payload)     [src/preload/index.ts:8]
  → ipcMain.handle(channel, wrapHandler(channel, handler))  [src/main/ipc/register.ts:21]
  → PERMISSION_MAP / auth.can(permission)                   [src/main/permissions-map.ts, src/main/auth.ts:25]
  → createXxxService(db).method(payload)                    [src/main/services/<域>/<域>.service.ts]
  → db.transaction(...) → Result<T>
```

**路径 B（LAN 客户端，v1.3 新增）**：

```text
renderer 同一组件 → window.api.invoke(channel, payload)     ★ renderer 完全不改
  → preload api 层路由：本地白名单通道走 IPC；
    其余通道在"LAN 模式"下走 lanClient.invoke(channel, payload)
  → HTTPS POST /api/v1/rpc/{channel}
    Header: Authorization: Bearer <session token>
            X-Request-Id: <uuid>（写操作）
  → 主机 auth.ts 校验设备+会话 → gateway.ts 按 PERMISSION_MAP[channel] 校验员工 RBAC
  → 主机复用同一个 createXxxService(db) 实例（与 IPC 路径同一工厂、同一 db）
  → db.transaction → Result<T> 原样 JSON 返回
```

关键论证（为什么 renderer 可零改动）：

1. **preload 已经是"通用 channel invoke"抽象**。`src/preload/index.ts` 暴露的只有一个方法 `api.invoke(channel, payload)`——renderer 从不直接触碰 ipcRenderer，也不 import 各服务的类型签名（类型在 `src/shared/types/`，两边共享）。因此"API 层从 window.api 切换到 HTTP 客户端"只需替换 preload 里的这一个函数的实现，renderer 的调用代码 `window.api.invoke('sale:create', {...})` 一个字符都不用改。
2. **业务规则已在主进程服务层**（AGENTS.md 红线 3），renderer 只做展示；channel 名即天然稳定的 API 契约（`PERMISSION_MAP` 已把全部 47+ channel 映射到权限键）。
3. 风险与对策见 §12.1（回归面：preload 层错误传播语义、本地专用通道白名单、事件推送差异）。

### 2.3 选型论证：主机 HTTP/WS 服务（D1）

候选 A：**Fastify + ws（@fastify/websocket）**

- 优点：Node 生态最成熟的 HTTP 框架之一；JSON Schema 校验内建；`fastify.inject()` 让单测不需要真实端口（§10）；ws 库经过大规模生产验证；TypeScript 支持良好；与 Electron 主进程同进程运行无原生模块问题。
- 缺点：依赖树较大（约 15 个传递依赖）；启动约 +30~60ms（对本项目无感，启动预算 3s）。

候选 B：**uWebSockets.js（uWS）**

- 优点：性能极高（C++ 内核），内存占用低，HTTP+WS 一体。
- 缺点：**不适合本项目**——① 无正式 TypeScript 类型（社区维护 @types 质量差）；② API 为回调风格，与现有 async/await 服务层集成需手工包装；③ 版本历史上有 breaking change 且 npm 发布曾中断；④ 本项目单主机 ≤3 客户端，性能冗余毫无意义；⑤ `AGENTS.md` YAGNI 原则：能用常规依赖解决就不引入非常规依赖。

候选 C（考虑过并放弃）：**裸 node:http + 自写路由**——省依赖但要把 body 解析、错误处理、路由分发全手写，测试成本高于收益。

**结论：选 Fastify + ws。** 门店规模 3 台设备，吞吐量差距 6 个数量级无意义；开发效率、类型、可测试性（`fastify.inject`）是硬指标。

相关版本约束（TBD：锁定具体 minor 版本于实施时）：

- `fastify@5.x`、`@fastify/websocket@11.x`（内置 ws@8）、`@fastify/cors`（仅允许同网段来源，或干脆不开 CORS——桌面客户端不跑浏览器，v1.3 不开 CORS）。
- TLS：自签证书，主机首次启动生成 Ed25519/EC P-256 自签证书（CN=主机实例 ID），客户端配对时指纹固定（§5.3）。

### 2.4 端口与防火墙

- 默认端口 **18650**（TCP），可在设置中改（1024–65535）。
- 绑定：默认 `0.0.0.0`；安装时以 `netsh advfirewall` 添加仅 Private profile 的入站规则（放行本程序路径）。若用户拒绝防火墙授权，主机服务仍启动但 UI 明确提示"局域网客户端将无法连接"。
- 主机不可达（关机/休眠）时客户端 UI 显示"门店主机不可用"，禁止正式单据提交（§6.4）。

### 3.2 gateway.ts：复用 IPC handler 表

现有 `src/main/index.ts` 用约 30 次 `registerIpc({...})` 注册了全部 channel。设计上**不重复维护两份 handler**：

1. 重构（行为不变）：把 `src/main/index.ts` 中各 `registerIpc(map)` 的 `map` 对象抽为模块级导出 `buildXxxHandlers(deps)`（或集中到 `src/main/ipc/handlers.ts`），IPC 注册与 HTTP gateway 都消费同一份对象。
2. `gateway.ts` 拿到 handler map + `PERMISSION_MAP`，对每个 HTTP 请求：
   - 校验会话与设备（auth.ts）；
   - `channel` 必须在 map 中（404）；
   - `PERMISSION_MAP[channel]` 存在时，校验当前登录员工（§5.5）的 RBAC；
   - 写通道（§4.3 清单）走 `lan-request-id.ts` 防重放；
   - `await handler(null, payload)` —— handler 签名 `(evt, payload)`（`src/shared/result.ts:19`），HTTP 路径 evt 传 `null`（现有 handler 均不读 evt，TBD：实施前用 grep 确认无 evt 使用，若有则抽 evt 依赖为参数）；
   - 返回 `Result<T>` 原样作为 HTTP 200 body（业务错误语义在 body 内，不用 HTTP 状态码区分业务失败——见 §4.1）。

3. 本机 IPC 路径与 HTTP 路径调用**同一个 handler 函数、同一个 service 工厂实例**，保证事务边界、权限、审计行为完全一致。

### 3.5 主机进程形态（D1/D4）

- 主机 = 普通 Electron 应用实例 + `src/main/host/server.ts` 在 `app.whenReady` 后 `listen(18650)`。主窗口关闭不退出进程（托盘常驻），业务服务持续可用——这满足"客户端关闭不停止服务"（上游设计 §2），不需要独立 Windows Service（统一安装包，客户双击即用，运维成本最低）。

## 4. HTTP API 契约

### 4.1 总则

- Base：`https://<host-ip>:18650/api/v1`
- **错误模型**：沿用 `Result{ok, code, msg, data}`（`src/shared/result.ts:1`）。业务失败一律 HTTP 200 + `result.ok=false`；传输/协议层错误才用 HTTP 状态码（401 未认证、403 权限/设备拒绝、404 未知 channel、429 限流、500 内部错误）。理由：renderer 现有错误处理全部基于 `Result`，双路径语义一致可让错误 UI 逻辑零改动。
- `BizError(code, msg)` 抛出后被 `wrapHandler` 转 `Result`，HTTP 层透传，不改写。
- 所有请求/响应体 JSON UTF-8；时间字段 ISO 8601 字符串（与现有 `datetime('now','localtime')` 存储习惯一致——见 §12.5 时间同步风险）。
- 内容长度上限 10MB（附件通道 `attachment:save` 走 base64，现状如此，保持）。

### 4.2 认证与系统端点

| Method | Path | Auth | 说明 |
|---|---|---|---|
| GET | `/health/live` | 无 | `{alive:true}`；不暴露版本/路径细节 |
| GET | `/health/ready` | 无 | 检查 db 打开、migration 版本、写可用性 |
| POST | `/pair/start` | 无（配对码即认证） | 客户端提交 `{pairingCode, deviceName}`；见 §5 |
| GET | `/pair/pending` | 主机本地 UI 轮询（本机 IPC `host:pairPending`） | 主机弹确认框的数据源，不经网络 |
| POST | `/auth/session` | 设备签名 | 设备证明 + 员工登录，返回 token（§5.5） |
| POST | `/auth/logout` | token | 作废当前会话 |
| WS | `/events` | token（query 或首消息） | 通知通道，§6 |

### 4.3 业务 RPC 端点

统一形态 `POST /rpc/{channel}`（channel 即现有 IPC channel 名，`:` 原样保留——URL 合法字符）。**不按 REST 资源建模逐个设计 `/products`、`/sales-orders` 端点**，理由：

1. 现有 47+ 权限键与约 300 个 channel 已在 `PERMISSION_MAP`（`src/main/permissions-map.ts`）形成稳定映射，channel 直通可让 HTTP 层校验逻辑与 IPC 层共享同一张表，不出现"两套权限语义漂移"。
2. 上游设计 §5.1 的 REST 路径是面向"增量同步服务器"的设计，本 spec 已决策不做 change_log（D2），REST 资源建模的收益（缓存语义、URL 语义）对桌面 RPC 场景无实际价值。
3. renderer 的调用点本来就是 channel 语义，直通映射让双路径行为可逐 channel 对拍测试。

### 4.4 幂等与防重放：command_results

客户端对**每个写请求**生成 `X-Request-Id`（UUID v4，提交前持久化到本地 `pending-request.json`，防止进程崩溃后丢失 ID）。主机端：

```sql
-- 080_command_results.sql
CREATE TABLE command_results (
  request_id   TEXT PRIMARY KEY,          -- 客户端 X-Request-Id
  channel      TEXT NOT NULL,             -- 业务通道名，防止不同业务撞 ID
  device_id    TEXT NOT NULL,
  request_hash TEXT NOT NULL,             -- sha256(channel + JSON.stringify(payload))，识别"同 ID 不同内容"
  result_json  TEXT NOT NULL,             -- 原 Result<T> 全文
  created_at   TEXT NOT NULL
);
CREATE INDEX idx_command_results_device ON command_results(device_id, created_at);
```

处理顺序（在主机事务外读、事务内写，TTL 清理由每日任务执行）：

1. `SELECT ... WHERE request_id=? AND channel=?`：
   - 命中且 `request_hash` 一致 → 直接返回 `result_json`（HTTP 200，body 加 `replayed:true` 标记）；
   - 命中但 hash 不一致 → 返回 `E_REQUEST_ID_CONFLICT`（同 ID 不同内容，客户端必须换 ID 并人工检查）；
2. 未命中 → 执行业务（service 内部 `db.transaction`）→ 成功或**业务失败**（`Result.ok=false` 且 code 属于确定性错误，如 `NOT_ENOUGH`、`NO_PERMISSION`）都写入 `command_results` → 返回。
3. 非确定性失败（网络中断前结果未知、进程崩溃）不写入：客户端以**原 ID 重试**，符合"未知结果的写请求必须用原幂等 ID 重试"（上游设计 §5.2，与 D3 不冲突——重试的是同一 ID，不是自动换单重发）。
4. 保留策略：90 天或每设备最近 1000 条，每日备份任务顺带清理。

库存扣减在业务事务内天然防重：同一 `sale:create` payload 重放时，第二次若不拦截会再次扣库存——`command_results` 必须在业务事务**同一事务内**插入（`INSERT OR IGNORE` + 读回判断），避免"业务提交成功但防重记录未写"的窗口。实现：`gateway.ts` 把防重检查与业务调用包进一个 `db.transaction(() => {...})`（better-sqlite3 支持嵌套 savepoint，语义安全）。

### 4.5 限流与审计

- 每设备每 channel 令牌桶：默认 30 req/s，超出 429 + `RETRY_AFTER`。收银高峰单客户端实际 <2 req/s，余量充足。
- LAN 写请求写现有 audit（`src/main/services/audit/audit.service.ts`），operator 记 `username@deviceId`。

## 5. 认证与配对

### 5.1 设计原则

- **设备身份**与**员工身份**分离：设备先证明"我是已配对的机器"，员工再登录"我是谁、有什么权限"（RBAC 复用现有 `user`/`access_role` 表，见 §5.5）。
- 配对必须主机店长物理在场确认（主机弹窗）。
- 配对码一次性、5 分钟 TTL、限尝试 5 次。

### 5.2 配对流程时序

```text
客户端                        主机（LAN 服务）                     主机本地 UI
  │ 1. GET /health/live            │                                  │
  │───────────────────────────────▶│ TLS 握手，客户端记录证书指纹候选    │
  │ 2. POST /pair/start            │                                  │
  │   {pairingCode, deviceName}    │                                  │
  │───────────────────────────────▶│ 校验码存在/未过期/未用尽           │
  │◀─────── {pending:true} ────────│ 进入待确认队列                     │
  │                                │──── 本机 IPC host:pairPending ───▶│
  │                                │        店长看到弹窗                │
  │                                │◀─── 店长点"允许"（或拒绝）─────────│
  │                                │ 生成 deviceId、32B secret、       │
  │                                │ 存 host_devices(sha256(secret))   │
  │ 3. 客户端轮询 GET /pair/result  │                                  │
  │───────────────────────────────▶│                                  │
  │◀── PairGrantResponse{secret,   │                                  │
  │     deviceId, certFingerprint} │                                  │
  │ 4. 客户端：secret 经 DPAPI 落盘  │                                  │
  │    userData/host-client.json   │                                  │
```

- 配对码生成：主机设置页点击"添加设备"→ 生成 6 位数字码（`crypto.randomInt(0, 1e6)`）+ 展示二维码（内容：`hesora-pair://<ip>:18650/<code>`）→ 5 分钟 TTL，过期作废重生成。存储于主机内存 + `host_devices` 待定字段（TBD：配对码存内存即可，不落盘）。
- 尝试限制：配对码一次性使用（confirm 成功即作废）；`/pair/start` 全局限流 10 req/min（实现裁定：错误码不在表内无法计数，限流即可达到防暴力猜测强度——1e6 码空间×10/min，TTL 5min 内命中概率≈6e-7）。
- 设备数上限：license `maxDevices`（含主机计 1）超出时拒绝并提示"设备数已达授权上限，请先解绑设备或扩容"。

### 5.3 TLS 与主机信任

- 主机首次启动生成自签证书（EC P-256，CN=hostInstanceId），私钥存 `userData/secrets/`（Windows 下建议 DPAPI 加密落盘，TBD：v1.3 用 DPAPI `CryptProtectData` 包一层）。
- 客户端在配对响应中拿到 `certFingerprint`（sha256 hex），此后每次 TLS 连接校验指纹固定（pinning），**不允许全局忽略证书错误**。指纹不符 → 连接失败并提示"主机身份异常"。
- 证书轮换：主机重装/手动重置后指纹变化，客户端必须重新配对（v1.3 不做静默轮换；TBD：v1.4 接力场景的证书迁移在另一 spec 定义）。

### 5.4 设备凭证：HMAC vs mTLS 论证（二选一）

| 方案 | 描述 | 优点 | 缺点 |
|---|---|---|---|
| A. HMAC 请求签名 | 设备持 `secret`；每次请求 `sig = HMAC-SHA256(secret, ts + nonce + body_sha256)` 放 header | 实现简单（纯 Node crypto）；无证书状态管理；审计友好；与 DPAPI 落盘搭配简单 | 秘密在每请求参与计算（不传输，风险可控）；无前向保密 |
| B. mTLS | 设备持独立客户端证书，主机 CA 签发 | 传输层双向强认证；密钥不出设备 | Electron `session.setCertificateVerifyProc` 定制校验复杂且与 fetch(Node undici) 的 mTLS 配置有坑；证书吊销/轮换状态机成本高；3 台设备规模下收益极低 |

**结论：选 A（HMAC）**。TLS 保证传输机密性与主机身份（§5.3 pinning），HMAC 保证设备身份与请求完整性，二者正交叠加即可达到 mTLS 的实际安全水平。3 台设备规模下 mTLS 的运维复杂度（证书生命周期）是纯负债。会话建立后改用 Bearer token（§5.5），HMAC 只在 `/auth/session` 一步出现，兼顾"秘密少用"与"实现简单"。

签名细节：

```text
/auth/session 请求头：
  X-Device-Id: <deviceId>
  X-Ts: <unix 秒>          // 主机校验 ±120s（含时钟容忍，见 §12.5）
  X-Nonce: <32B hex，一次性>   // 主机侧防重放为内存 Map（TTL ±120s 窗口；实现裁定：重启清空可接受，重放窗口不超 ±120s）
  X-Sig: hex(HMAC-SHA256(secret, "session" + deviceId + ts + nonce + sha256(body)))（实现裁定：hex 与 body_sha256/secret/fingerprint 编码统一，弃 base64）
```

### 5.5 会话与员工登录

```text
POST /auth/session  {deviceId, employee: "admin", password: "…"}
  → auth.ts: 校验 HMAC（§5.4）→ 校验 host_devices 未 revoked
  → 校验员工：复用 user 表（src/main/db/migrations/005_user.sql，scrypt password_hash）
  → 生成 session token（32B 随机，存 host_sessions，8h TTL，滑动续期：每次请求刷新 last_seen）
  → 返回 {token, expiresAt, user, permissions[]}   // permissions 由 access_role.permissions 解出
```

- **员工 RBAC 复用现有体系**：`user` 表 + `access_role` 表（`015_access_roles.sql`）+ `roleHas()`（`src/shared/permissions.ts`）。HTTP 层的权限判定与 IPC 层一致：`PERMISSION_MAP[channel]` → `roleHas(user.role, permission, user.permissions)`。
- LAN 客户端登录界面复用现有登录组件（员工选择+密码框，仅数据源换成 `/auth/session`）。
- token 过期：HTTP 401 + `code:'SESSION_EXPIRED'` → 客户端 lan-state 转入重连状态机，自动用设备凭证重新登录取新 token（员工密码不重输，8h 内）。
- 会话管理表：

```sql
-- 082_host_sessions.sql
CREATE TABLE host_sessions (
  token_hash  TEXT PRIMARY KEY,        -- sha256(token)，不存原文
  device_id   TEXT NOT NULL,
  user_id     INTEGER NOT NULL REFERENCES "user"(id),
  created_at  TEXT NOT NULL,
  last_seen_at TEXT NOT NULL,
  expires_at  TEXT NOT NULL,
  revoked_at  TEXT
);
```

- 踢出：主机端"已连接设备"页可吊销设备（`host_devices.revoked_at`）→ 该设备全部会话作废、WS 断开；设备重新配对才可恢复。员工密码修改/禁用 → 该用户全部会话立即作废。

### 5.6 设备表

```sql
-- 081_host_devices.sql
CREATE TABLE host_devices (
  device_id      TEXT PRIMARY KEY,     -- uuid
  device_name    TEXT NOT NULL,
  secret_hash    TEXT NOT NULL,        -- sha256(secret 原始 32 字节)，非 hex 字符串的 sha256（写死防客户端侧实现踩坑）
  paired_at      TEXT NOT NULL,
  revoked_at     TEXT,
  last_seen_at   TEXT
);
```

## 6. WS 通知协议

### 6.1 消息类型

```ts
// src/shared/host-protocol.ts
export type DocChangeSummary      = { docType: string; docId: number; action: 'create'|'review'|'reverse'|'update' }
export type InventoryChangeSummary= { productId: number; warehouseId: number; reason: string }  // 不带数量（避免泄露给仅 view 权限外的会话）
export type MasterChangeSummary   = { entity: 'product'|'customer'|'supplier'|'warehouse'|'fund'|'setting'; id?: number }
```

| type | 方向 | 触发点 | payload |
|---|---|---|---|
| `doc.changed` | S→C | sale/purchase/retail/doc:review/doc:reverse 等 handler 成功返回后 | 只发类型+概要，**不推全量单据数据** |
| `inventory.changed` | S→C | 任何库存变动（含 cost_log 写入的通道） | productId+warehouseId 概要 |
| `master.changed` | S→C | 主档 create/update/disable | 实体名+id |
| `ping` | C→S | 客户端 25s 一次 | `{ts}` |
| `pong` | S→C | 对 ping 响应 | `{ts}` |

设计要点（D2 落地）：

1. **通知不承载数据**：客户端收到后调用对应查询接口刷新当前页（商品列表页刷新 `product:query`，单据页刷新 `doc:query`，收银页刷新条码商品的库存摘要）。理由：不做 change_log（D2）后无法可靠增量，全量刷新当前页（分页 ≤50 条）成本可忽略；避免"通知数据与刷新数据不一致"的第二真相源。
2. **通知不保证必达**：WS 只是优化体验（减少手动刷新）；断线重连后客户端无条件全量刷新当前视图与看板。协议层不做 seq/ack。
3. 广播粒度：按会话权限过滤——无 `product.view` 的会话不收 `master.changed`（实现：ws-hub 持每连接的 permission 集合，广播前过滤；3 连接规模无性能问题）。

### 6.2 ws-hub.ts

- Fastify `@fastify/websocket` 路由 `/api/v1/events`；连接建立时校验 token query 参数，失败 1008 关闭。
- 心跳：客户端 ping 25s，服务端 60s 未收到任何帧则断开（ws 库 `heartbeat` 模式）。
- 服务端广播 API：`wsHub.broadcast(msg, filter?)`，由各 service 调用点触发——**不在 service 内调用**（保持 service 无 WS 依赖），而是在 `gateway.ts` / IPC bridge 包装层按 channel → 事件映射表发出（如 `sale:create` 成功 → `doc.changed` + `inventory.changed`）。映射表集中在 `gateway.ts`，与 PERMISSION_MAP 相邻维护。

### 6.3 重连

- 客户端指数退避：1/2/4/8/16/30s + jitter（±20%）。
- 重连成功（含 `/auth/session` 重新取 token）→ 触发 lan-state `refreshAll` 事件 → renderer 当前路由组件监听并重拉数据。

### 6.4 客户端连接状态机

```text
DISCONNECTED ──发现/配置主机──▶ CONNECTING ──TLS+配对有效──▶ AUTHENTICATING ──▶ CONNECTED
                                      │                        │                   │
                                      │ TLS/指纹失败            │ 设备被吊销/凭证失效  │ WS 断开或 HTTP 401/网络失败
                                      ▼                        ▼                   ▼
                                 ERROR(需重配对)          ERROR(需重配对)      RECONNECTING（退避）
                                                                                  │ 连续失败 > 60s
                                                                                  ▼
                                                                              HOST_UNREACHABLE
```

`HOST_UNREACHABLE` 下：可浏览本地缓存（商品/库存的最近一次查询结果，localStorage），所有写通道 UI 禁用并提示"门店主机不可用"；**不承诺离线开单**（非目标 §1.2）。

## 7. 加密备份（v1.3 范围）

> v1.4 云盘上传（Provider 适配、OAuth、分片、checkpoint）见 `docs/alist-provider-research.md`，本节只定义容器格式、加密与本地流程，并把上传留作 `CloudProvider.upload()` 的单一接口位。

### 7.1 INVBAK v1 容器格式

```text
偏移   字段                 大小        说明
0      magic               4B          'IVBK'
4      format_version      2B          = 1（小端）
6      kdf_alg             1B          = 0x01 (Argon2id)
7      kdf_mem_kib         4B          小端，默认 65536 (64 MiB)
11     kdf_iters           4B          小端，默认 3
15     kdf_parallel        4B          小端，默认 1（实现裁定：u32 与相邻字段对齐，1B 非常规）
16     salt                16B         每备份随机
32     aes_iv              12B         AES-256-GCM IV，每备份随机
44     ciphertext_len      8B          小端，后面密文块字节数
52     ciphertext          变长        gzip( SQLite 快照 ) 经 AES-256-GCM 加密
...    auth_tag            16B         GCM tag（追加在密文尾部，node crypto 默认位置）
...    meta_json           变长        明文，长度=文件总长−尾部偏移（隐式得出，无独立 len 字段——实现裁定：见 2026-11-09 审查裁决）
```

`meta_json`（明文，供恢复前预览与版本校验；禁止含手机号/单据明细/token）：

```json
{
  "backupId": "uuid",
  "storeName": "…",
  "createdAtUtc": "2026-11-09T08:00:00Z",
  "dbSchemaVersion": 70,            // user_version 快照值
  "appVersion": "1.3.0",
  "sourceInstanceId": "uuid",       // 主机实例标识（v1.4 接力用）
  "snapshotSha256": "hex",          // 密文的 SHA-256（完整性清单）
  "sizeBytes": 123456
}
```

密钥派生：`key = Argon2id(userPassphrase, salt, mem, iters, parallel)` → 32B AES-256-GCM key。用户口令在设置备份时输入（另支持"自动密钥"模式：口令存 DPAPI，仅本机可解——落盘云盘时强制用户自设口令，防止恢复依赖本机 DPAPI）。

完整性清单：`snapshotSha256` 在 meta 中，恢复流程先验 SHA-256 再解密验 GCM tag，两道校验缺一即拒绝恢复。

### 7.2 算法与依赖

- 候选 1：**Argon2id**（`argon2` 原生模块或 `@noble/hashes` 纯 JS）——抗 GPU 暴破，2015+ 密码哈希竞赛胜者，备份口令是低熵人输口令，必须用记忆困难函数。
- 候选 2：PBKDF2-HMAC-SHA256（Node 内建）——零依赖，但抗暴破显著弱。
- **选 Argon2id**；依赖优先 `@noble/hashes`（纯 JS，免原生编译，electron-builder 无 ABI 风险；64MiB/3 轮在 JS 实现约 1~3s，备份场景可接受；若实测 >5s 换 `argon2` 原生模块）。AES-GCM 用 `node:crypto` 内建，零依赖。

### 7.3 备份流程

```text
触发（手动 / 每日定时复用现有 dailyBackup 时刻，src/main/services/backup/backup.service.ts:80）
 → 队列（独立 async 队列，串行；备份中收银不受影响——better-sqlite3 WAL 读写并发）
 → 1. 快照：vacuumInto()（现有函数，backup.service.ts:19，即 SQLite Online Backup 的 VACUUM INTO 形式）
      到 userData/tmp/<backupId>.db；校验 PRAGMA integrity_check
 → 2. gzip → 3. Argon2id+AES-256-GCM 加密 → <name>.invbak 落盘到用户指定目录
 → 4. 写 backup_v2 历史（083_backup_v2.sql：backup_id, path, meta_json, state, created_at）
 → 5.（v1.4）CloudProvider.upload(path, data) —— 本版留接口位，type 仅为 'local'
 → 6. UI 显示"最近成功备份时间"；失败显示原因，不阻断收银
```

- 快照并发限制：同一时刻最多 1 个快照任务；与现有 `applyPendingRestore`（启动时恢复检查）互斥。
- 保留策略：按现有设置"保留最近 N 份"轮替删除本地 `.invbak`；手动备份不自动删。

### 7.4 恢复流程与版本兼容

```text
选择 .invbak → 读 meta_json → 校验 snapshotSha256 → 输口令 → Argon2id 派生 → GCM 解密
 → gunzip → 写临时文件 → integrity_check
 → 版本校验：meta.dbSchemaVersion ≤ 当前 migrations 目录最大 user_version（否则拒绝："备份来自更新版本，请先升级软件"）
 → 复用现有 restoreFrom（backup.service.ts:91）与 applyPendingRestore 落地机制（下次启动替换 db）
 → 危险操作二次确认 + 写操作日志（AGENTS.md §5）
```

### 7.5 与 v1.4 的边界

- 本版落盘接口：`encryptSnapshot(db, passphrase, outPath)` 纯函数，v1.4 云盘任务直接复用，容器格式不变（`sourceInstanceId` 字段已预留）。
- 双机接力（handoff）、云盘 Provider 状态机、manifest 提交协议均不在本 spec，见上游设计 §7.5/§8 与 `docs/alist-provider-research.md`。

### 7.6 现有 sync 快照格式的关系

现有 `sync.service.ts` 的 `hesora-inventory.zjsnap`（gzip+明文 sha256 manifest，无加密）保留用于双机同步旧场景与恢复兼容；v1.3 起新备份统一走 INVBAK v1。不做 zjsnap→invbak 迁移（旧快照仍可恢复，新备份全部加密）。

## 8. 并发与事务边界

### 8.1 主机端串行化模型

better-sqlite3 是同步 API，单连接单写者；现有所有库存变动走 `db.transaction`（AGENTS.md §4）。因此：

- **并发卖最后一件**（D3）：两个客户端的 `sale:create` 到达主机后，即使 IPC/HTTP 并发进入，better-sqlite3 在 JS 单线程内串行执行事务；后到者在库存预检时 qty 已被扣减，抛 `BizError('NOT_ENOUGH', '库存不足：…')`（现路径已覆盖：`src/main/services/sale/sale.service.ts:111`、`inventory.service.ts:142`、`transfer.service.ts:70`、`assemble.service.ts:124`）。**不做重试/排队等待**，直接失败提示——收银场景语义正确（单子没收钱就不会出错账），且实现零新增。
- 确认项：sale 事务内预检+扣减在同一事务（`sale.service.ts` 头注释明确"二者写在一个事务里"），WAL 下无脏读窗口。
- 主机与 LAN 客户端请求共享同一 service 实例与同一连接，无第二个写连接（备份快照 `VACUUM INTO` 是只读拷贝，不写主库）。
- 长事务防护：禁在事务内做网络/打印/备份（现状遵守，gateway 层不引入新违例）。

### 8.2 客户端并发编辑主档 = 最后写入者胜

商品/客户/供应商等主档按 id `UPDATE` 全字段覆盖，两客户端同时编辑 → 后提交者胜，无版本冲突检测。**接受理由**：

1. 主档编辑低频（新店建档期密集，日常 ≤ 几次/天），同字段同时编辑概率极低；
2. 主档字段无资金/库存敏感性，覆盖错可手工改回；
3. 引入 optimistic version 字段需改全部主档表 + 全部编辑 UI 的冲突提示流，成本远超收益（YAGNI）。
4. 缓解：`master.changed` WS 通知会让另一端列表页自动刷新，能更快发现"我改的被覆盖了"（提示信息 TBD：v1.3 不做行级冲突 UI）。

### 8.3 禁 SMB 直写（重申）

客户端进程**永不**打开主机机器上的 db 文件路径，不使用任何网络文件系统访问数据库。数据访问的唯一通道是 HTTP API。安装文档明确：数据库所在目录不要放网盘同步目录/共享目录（上游设计 §2）。`command_results`/会话表均在主机本地。

### 8.4 幂等与并发的交互

同一 X-Request-Id 并发到达（客户端双击重试）：`command_results` 主键 + 业务事务串行 → 第二个请求读到已存在记录返回原结果，业务只执行一次（§4.4 的"同事务插入"设计保证）。

### 9.2 License 扩展（D5）

`src/shared/license.ts` 现有 `LicensePayload{customer, issuedAt, expiresAt, machine}`，Ed25519 签名（`generateLicenseCode`，`license.ts:60`）。扩展：

```ts
export interface LicensePayload {
  customer: string
  issuedAt: string
  expiresAt?: string | null
  machine?: string | null
  // v1.3 新增（旧授权码缺省时按 {edition:'standard', features:[], maxDevices:1} 处理）
  edition?: 'standard' | 'professional'
  features?: Array<'lan_collaboration'|'cloud_backup'|'multi_warehouse'|'rbac'|'device_handoff'>  // device_handoff 为 v1.4
  maxDevices?: number              // 含主机；standard 缺省 1
}
```

运行时检查（主机启动路径，`src/main/index.ts`）：

```text
app ready → license service 解析授权（现有 createDesktopLicenseService）
 → payload.features 含 'lan_collaboration' 且未过期
   → createHostServer(...)  注册 HTTP/WS、加载配对数据
 → 否则：不创建 server、不监听端口、不注册 Tray 主机图标，基础版行为与 v1.2 完全一致（零开销）
 → 试用态（trial/extended）：允许 LAN 功能试用（商业策略 TBD：试用是否含 LAN，倾向允许，7 天试用即体验专业版）
 → 过期 expired：host server 停止接收新业务请求（/rpc 一律 NO_PERMISSION），保持 health/live 供客户端显示"授权过期"
 → 客户端侧：lanClient 需 license 有 lan_collaboration 才显示"连接主机"入口；standard 装机当纯单机用，无任何 LAN UI
```

激活服务器签发侧（`server/` 目录）同步增加 edition/features/maxDevices 字段——签发 CLI 用同一 `generateLicenseCode`，向后兼容（旧码字段缺省走 standard 分支）。

### 9.3 基础版安装包行为

统一安装包（D1），不区分 base/pro 两个包；差异只在授权数据。无 `lan_collaboration` 时：

- 不加载 fastify（懒 import，`host/server.ts` 仅在 feature 判定通过后 `await import()`）；
- 新增 4 张表空置；
- 新增依赖不打进主 bundle 关键路径（electron-vite 分 chunk，不影响启动 <3s 目标）。

### 9.4 升级路径

v1.2 → v1.3 就地升级：migration 080-083 追加；不改动现有表结构；`Result`/channel 语义不变 → 老客户端无 LAN 概念，升级后仍是单机，行为不变。

## 12. 风险清单

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R1 | **renderer API 层切换回归面大**：约 300 channel 走 HTTP，任何一处的 payload 序列化差异（undefined/Date/大整数）都可能出错 | 高 | ① preload 层 JSON 规范化沿用现有 `JSON.parse(JSON.stringify(payload))`（`src/preload/index.ts:5`）；② T1 表驱动对拍：同一 payload 分别走 IPC 与 HTTP，断言 Result 深度相等；③ 灰度：先只开商品查询+销售通道，其余按周放量 |
